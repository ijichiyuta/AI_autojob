# 案件応募・納品エージェント 要件定義書

最終更新: 2026-09-12

> これは本人が書いた元の要件定義。実装時に判明した事実に基づく変更点は [revisions.md](revisions.md) にまとめている。

---

## 1. 概要

クラウドソーシングサイト（クラウドワークス／ランサーズ）上の案件を自動で収集・スコアリングし、応募文および納品物までをAIが生成する。人間は「応募してよいか」「納品してよいか」の2点のみをWebダッシュボードで判断する。

### 1.1 設計原則

1. **判断と責任は人間が持つ。** 応募・納品の確定は必ず人間の承認を経る。自動送信はしない。
2. **AI利用を隠さない。** クライアントから問われた場合は正直に答える。「AI使用不可」と明記された案件には応募しない（自動除外を必須実装とする）。
3. **量より通過率。** 応募数を増やすより、スコアリング精度を上げて勝率を取る。レビューが形骸化した時点でこのシステムは失敗とみなす。

### 1.2 スコープ外

- クライアントとのメッセージ返信の自動化（**意図的に対象外**。要件ヒアリング・修正対応・AI利用の可否確認は人間が行う）
- 契約・検収・請求の操作
- 新規アカウント作成

## 2. システム構成

### 2.1 実行環境

手元のMacで常駐。ダッシュボードとDBはクラウドに置き、外出先からも承認できる構成とする。

```
[手元PC] 常駐ワーカー (Node.js + Playwright)
    │  収集 / 応募送信 / 成果物生成
    ▼
[Supabase] Postgres + Storage + Auth
    ▲
    │  閲覧・承認
[Next.js ダッシュボード] Vercel
```

### 2.2 技術スタック

| 層 | 採用 |
|---|---|
| ワーカー | Node.js 22 / TypeScript / Playwright |
| スケジューラ | node-cron（常駐プロセス内） |
| DB | Supabase (Postgres) |
| ファイル保管 | Supabase Storage（成果物・スクショ） |
| ダッシュボード | Next.js (App Router) / Tailwind / shadcn/ui |
| 生成 | Claude API（応募文・記事）/ Claude Agent SDK（コード生成） |
| 通知 | ダッシュボード内 + ブラウザPush（任意でLINE Notify） |

## 3. ブラウザ操作方式

### 3.1 結論：Playwright + 実Chromeプロファイル（persistent context）

- 普段使いのChromeプロファイルを指定することで、**ログイン状態と2段階認証をまたがずに済む**。セッションCookieの保守が不要になる。
- `headless: false` で運用する。ヘッドレスは検知されやすく、また動作を目視確認できる利点が大きい。
- 常駐バッチとの相性がよく、失敗時のリトライ・スクリーンショット保存を組み込みやすい。

> 実装では専用プロファイルに変更した。理由は [revisions.md §3.1](revisions.md)。

### 3.2 採用しなかった案

| 案 | 不採用の理由 |
|---|---|
| Claude in Chrome（公式拡張） | 人間の対話操作が前提で、常駐バッチ化に向かない。ただし**セレクタが壊れたときの手動リカバリ用**として併用価値あり |
| 自作Chrome拡張 | サイト改修のたびに拡張側を保守する必要があり、Playwrightに対する優位性がない |

### 3.3 運用上のガードレール（必須実装）

- 収集クロールは **1ページあたり3〜8秒のランダム待機**。同時並行アクセスはしない。
- 収集は1日4回程度のバッチ（例: 9時 / 13時 / 17時 / 21時）。常時ポーリングはしない。
- 応募送信は **1日あたり上限10件**、送信間隔は5〜30分のランダム。
- 深夜1時〜7時は全処理を停止。
- ログイン失敗・CAPTCHA検知時は即座に停止し、ダッシュボードにアラートを出す。自動突破は試みない。

> **確認事項:** クラウドワークス／ランサーズ双方の利用規約の禁止事項に、自動化ツールによるアクセスに関する条項がないか、実装前に必ず一読すること。
> → 確認済み。結果は [revisions.md §3.5](revisions.md)。

## 5. 機能要件

### 5.1 案件収集

- プラットフォームごとに **アダプタパターン**で実装する（`CrowdWorksAdapter` / `LancersAdapter`）。共通インターフェース: `search()` / `fetchDetail()` / `submitApplication()`。
- 検索条件はDBに保持し、ダッシュボードから編集可能にする（カテゴリ、最低予算、新着のみ、など）。
- 既に `external_id` が存在する案件はスキップ。

### 5.2 スコアリング

**即時除外（`ng_filtered`）とする条件:**

- 案件文に「AI使用不可」「AI生成物不可」「AIツール禁止」等の記載
- 常駐・出社・稼働時間拘束が必須
- 予算が下限（設定値。例: 30,000円）未満
- 時給換算が設定値（例: 3,000円）未満
- 契約前のテスト課題が無償
- クライアントが本人確認未完了、かつ発注実績0

**加点項目（重み付けはconfigで可変に）:**

| 項目 | 重み |
|---|---|
| 時給換算 | 30 |
| クライアント評価・発注実績 | 20 |
| 現在の応募数の少なさ | 15 |
| 案件文の具体性（要件が明記されているか） | 15 |
| 得意ジャンルとの一致度 | 10 |
| 納期の余裕 | 10 |

案件文の具体性の判定はClaude APIで行う。要件が曖昧な案件はヒアリング工数が膨らむため減点する。

### 5.3 応募文生成

- 案件文・スコア内訳・過去の受注実績を入力にClaude APIで生成。
- **プロフィールおよび応募文テンプレートに、AIツールを活用している旨を明記する。** これは隠す運用を避けるためであり、同時に短納期・低単価の根拠として差別化材料にもなる。
- 提示価格と納期も併せて生成し、人間が編集可能な状態でダッシュボードに出す。

### 5.4 成果物生成（ジャンル別）

| ジャンル | 生成フロー |
|---|---|
| Web制作・LP | 要件整理 → 構成案 → Next.js/静的HTML生成 → Playwrightでスクショを撮りセルフレビュー |
| システム・アプリ開発 | 要件整理 → 設計 → Claude Agent SDKでリポジトリ生成 → テスト実行 |
| ライティング | 構成案 → 本文 → 事実確認（要出典箇所の抽出）→ 文字数・レギュレーション検証 |

いずれも `pending_delivery` で停止し、人間のレビューを待つ。

### 5.5 ダッシュボード

**承認キュー画面（中核）**

- カード1件 = 1案件。案件文・スコア内訳・生成された応募文・提示価格を1画面に収める。
- 操作は「承認」「編集して承認」「却下」の3つ。却下時は理由を選択（低単価／要件不明瞭／ジャンル不一致／クライアント不安／その他）。
- **承認ボタンには当日の残り応募枠を表示する**（例: 本日 3 / 10）。

**納品レビュー画面**

- 成果物のプレビュー（HTMLはiframe、コードは差分表示、記事は本文表示）。
- ジャンル別のレビューチェックリストを表示し、**全項目チェックしないと承認ボタンを押せない**仕様とする。これがレビュー形骸化に対する唯一の歯止めになる。

**その他の画面**

- 案件一覧（フィルタ・検索）
- 稼働状況（今日の収集件数・応募件数・進行中の案件）
- 実績（応募数 / 受注数 / 通過率 / ジャンル別・単価帯別の勝率）
- 設定（検索条件、スコア重み、上限値、NGワード）

## 6. 非機能要件

- **ログ:** 全ブラウザ操作を構造化ログに記録。応募送信時は送信直前のスクリーンショットをStorageに保存する。
- **セレクタ耐性:** DOMセレクタは設定ファイルに外出しする。取得失敗が一定回数続いた場合は該当アダプタを自動停止し、アラートを出す。
- **冪等性:** 全バッチは再実行可能に。応募送信は `applications.status` で二重送信を防止する。
- **秘密情報:** ログイン情報はChromeプロファイル内に閉じ、コードやDBには保持しない。APIキーは `.env`（gitignore対象）。

## 7. 実装フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| 1 | 収集＋スコアリング＋案件一覧画面 | 両サイトから案件が毎日DBに溜まり、スコア順に閲覧できる |
| 2 | 応募文生成＋承認キュー＋応募送信 | ダッシュボードで承認した案件が自動で応募される |
| 3 | 成果物生成＋納品レビュー画面 | 1ジャンルで納品まで通る |
| 4 | 残りジャンル対応＋実績分析 | 通過率が計測でき、スコア重みを調整できる |

**Phase 1 を2週間で通すことを最優先とする。** ここで溜まったデータを見れば、そもそも応募自動化に投資する価値があるか（＝スコア上位の案件が十分な数あるか）が判断できる。

## 8. リスクと対応

| リスク | 対応 |
|---|---|
| 規約上の自動化制限 | 実装前に両サイトの禁止事項を確認。上限・待機時間を保守的に設定 |
| DOM変更による収集停止 | セレクタ外出し＋失敗検知アラート。手動リカバリ用にClaude in Chromeを併用 |
| レビューの形骸化 | 納品承認にチェックリスト必須化。1日の納品上限も設ける |
| AI不可案件への誤応募 | NGワード判定を二重化（正規表現＋LLM判定）。どちらか一方でも該当したら除外 |
| 低単価案件で工数だけ溶ける | 時給換算の下限を絶対条件とし、例外を作らない |
